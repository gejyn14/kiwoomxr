## Import, configure, generate, test, build

From the repository root:

```bash
export UNITY_EDITOR="$HOME/Applications/UnityEditors/6000.0.67f1/Unity.app/Contents/MacOS/Unity"
./scripts/unity.sh import
./scripts/unity.sh configure
./scripts/unity.sh scene # First generation only; skip when using the committed scene.
./scripts/unity.sh validate
./scripts/unity.sh test
./scripts/unity.sh build
```

Run each command only after the previous one succeeds. Configuration uses the new Input System; restart when Unity requests it. Separate processes above also allow settings to reload before scene generation/build. Resolve any real package/compiler errors before proceeding.

The corresponding menu is **Spatial Trading** inside Unity. Scene generation uses public `OVRQuickActionsAPI` and `QuickActionsAPI` from the pinned SDK to create the standard comprehensive rig and its poke, ray and grab connections. It refuses to overwrite an existing `FocusShell.unity`; open/edit that scene normally. For intentional regeneration, first preserve the existing scene under a new path, then rerun generation.

Save open scenes and leave Play Mode before validation or building. The validator refuses unsaved changes instead of discarding them or building older on-disk scene data. If SDK setup changes a scene when loading it, review and save that change before running validation again.

Generated scene: `quest/Assets/SpatialTrading/Scenes/FocusShell.unity`.
Generated XR settings and Korean font assets: `quest/Assets/Generated/`.

After the first successful import/generation, retain Unity-created `.meta` files, scene, settings, TMP resources, generated font assets, and the package lock together. Do not copy `Library`, `Temp`, `Logs`, private settings, or build outputs into source control. These generated assets are now present. The scene generator waits for the asynchronous TMP Essential Resources import before creating the Korean font and scene.

Expected APK: `quest/Builds/Android/SpatialTrading-Shell.apk`.
Logs/XML/hash: `artifacts/milestone1/unity/`.

Inspect the final APK with the matching SDK:

```bash
python3 scripts/inspect_apk.py \
  --aapt "$HOME/Applications/UnityEditors/6000.0.67f1/Unity.app/Contents/PlaybackEngines/AndroidPlayer/SDK/build-tools/36.0.0/aapt"
```

This checks the expected manifest, ARM64/IL2CPP, absent Operator artifacts/private configuration filenames, and known local SDK token bytes without printing tokens. A missing local token is reported as `NOT_RUN_NO_LOCAL_TOKEN`. The SDK restores its Editor settings after building, so a local nonempty development token is not evidence that the emitted APK contains it.
Each new Unity invocation creates a unique timestamped subdirectory containing `editor.log`, `exit-code.txt`, and applicable test XML/APK hash. Retries preserve previous results. The original licensing failure predates these subdirectories and remains in `artifacts/milestone1/unity/import.log`.

The build is a development APK with the default development signing setup. The SDK's DevAgent settings remain ignored locally; `BuildCredentialGuard` disables that assistant and clears its local connection credentials after the SDK build callback runs. The guard also excludes the SDK Operator Android AAR, keeping simulation tooling and its capture/legacy permissions out of this APK. Final APK inspection verifies both exclusions. Distribution signing and store submission are outside Milestone 1. Inspect the generated Android manifest before installing: passthrough and optional hands/controllers are expected; eye tracking, camera-image access, brokerage credentials, and order capabilities are not part of this shell. Passthrough composition does not require giving the application raw camera images.

## Install and verify on Quest 3

Enable developer mode, connect USB, and approve the headset's debugging prompt. Run `adb devices -l`; it must show an authorized device. With one intended device connected:

```bash
adb install -r quest/Builds/Android/SpatialTrading-Shell.apk
adb shell monkey -p com.kiwoomxr.spatialshell -c android.intent.category.LAUNCHER 1
```

If more than one device is connected, use `adb -s` with the intended local device ID. Keep device IDs out of published evidence. Follow the [acceptance checklist](MILESTONE_1.md#headset-acceptance) in a comfortable seated setup. APK installation alone is not acceptance.

## Input and layout

- Direct poke/touch on the reachable control dock.
- Standard hand ray plus pinch at distance.
- Standard Meta controller interaction as fallback.
- Grab the clearly marked top handle to move a component.
- Grab a chart/secondary handle with both hands to resize (0.85–1.35 of initial size).
- Use **앞으로 정렬** to place surfaces in front of the current head direction.
- Layout is placed once from tracked head pose and remains world-stable. Head orientation is used for placement only, never called eye gaze.

The chart begins 0.95 m forward, 0.10 m below the head. The dock begins 0.57 m forward, 0.38 m below, tilted toward the user. A single secondary surface appears to the right. These are authored starting values, awaiting real ergonomic testing. No room/desk collision inference is implemented.

`ShellInputSources` records the active OVR hand/controller mode when an ISDK pointer activates a UI control; simultaneous-source attribution is not independently verified. It is diagnostic metadata and is **not physical-order-confirmation evidence**. A future confirmation adapter must implement the dedicated order safety contract.

## Editor simulator without a headset

Install the matching [Meta XR Simulator for Mac ARM](https://developers.meta.com/horizon/downloads/package/meta-xr-simulator-mac-arm/) (205.0 in this session) and launch it. Open the pinned Unity project, leave Play Mode, and use **Spatial Trading → 5. Run in Meta XR Simulator**. The launcher uses the SDK's Simulator and Operator activation menus, validates the saved scene and starts Play Mode. Menu **6. Stop simulator verification** exits Play Mode. Disable Operator/Simulator through their Meta menus after verification if no longer needed.

`SimulatorSession` writes read-only state snapshots to ignored `artifacts/milestone1/simulator/state.json` while recording. It neither dispatches shell actions nor enters the APK. Operator can supply controller poses/inputs through its OpenXR layer; resulting state and compositor captures must both be checked. Simulation does not establish real passthrough, hand tracking, performance, reach or comfort on Quest 3.

SDK reference: [Meta XR Simulator](https://developers.meta.com/horizon/documentation/unity/unity-simulate-xrsim/).

An Editor session that recompiled scripts and then re-entered Play Mode produced SDK lifecycle exceptions during development. The successful simulator verification used a fresh Editor process. Do not treat hot reload or repeated Play Mode lifecycle as verified; if SDK initialization fails, preserve the failure and restart the Editor before retrying. Quest lifecycle checks remain open.
